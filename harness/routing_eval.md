# 🧪 Routing Eval (라우팅 회귀 평가)

> **harness 위계 도구** — 사역 작업 도구가 아니라 *시스템 품질 보증* 도구입니다. 프롬프트 시스템도 회귀합니다: 측정 없는 다중 스킬 라우터는 새 스킬 추가에서 조용히 무너집니다. (스킬 수의 현행 값은 루트 `CLAUDE.md` 워크플로우 절이 SSOT — 여기서는 고정 숫자를 다시 적지 않는다.)

## 실행 시점

1. `skills/`에 스킬을 추가·제거·이름 변경했을 때
2. `skills/00_pastor_concierge/SKILL.md`의 라우팅 규칙을 수정했을 때
3. 정기 점검 (분기 1회 권장)

## 평가 절차

1. **입력/기대답 분리**: 진행자가 `tests/routing_cases.md`를 읽어 ID·발화만 포함한 입력 파일과 ID·기대 스킬·비고의 정답 파일을 별도로 만든다. 실행자는 골든셋 원본·정답 파일·핸드오프·이전 평가 결과를 열지 않는다.
2. **새 컨텍스트 실행**: 실행자에게 Concierge 지침과 스킬 인벤토리, 입력 파일만 제공한다. `journal:` 조건은 그대로 전달한다. 각 사례마다 판단을 독립적으로 기록하고 질문이 필요하면 질문과 예정 경로를 함께 쓴다. 전문 제작은 이 라우팅 테스트 범위가 아니다.
3. **답 고정 후 대조**: 실행 결과를 파일로 고정한 다음 진행자가 기대답과 대조한다. 라우트와 행동 조건(무질문·범위 밖·제공 범위 등)을 구분해 일치/불일치/부분/판정 보류를 기록한다. `(모호)`는 실제 필요한 확인을 했는지 본다. 정답에 맞추어 이미 저장한 답을 수정하지 않는다.
4. **회귀와 효용 분리**: 기존 1~88과 새 회귀 사례를 별도 집계한다. 새 사례는 구현자가 만든 계약 회귀이며 독립 사용자 표본이 아니다. 불일치는 해당 입력·실제 답·기대·지침 근거로 분석한다. 수정 후 새 실행은 별도 파일에 남긴다.

## 출력 포맷

```markdown
# 🧪 Routing Eval Report ({date})

**정확도: {N}/{총} ({%})** — 기준: 90% 미만이면 Concierge 라우팅 규칙 점검 필요

## 오답 목록
| # | 발화 | 기대 | 실제 판정 | 원인 분석 |
|---|---|---|---|---|

## 권고
- {라우팅 규칙 §N에 키워드 패턴 추가 등 구체 수정안}
```

## 한계 고지 (정직)

- 기대답을 분리해도 같은 모델 계열과 설계자가 만든 사례의 편향은 남으며 실제 사용자 발화 분포와 다를 수 있다. 결과를 고정하기 전에 정답을 본 실행은 격리 평가로 집계하지 않는다. 90% 통과가 품질 보증이 아니라 **회귀 감지선**이다.
- 결과 저장: 사용자가 요청할 때만 `outputs/{date}/_eval/routing_eval_{date}.md`.
